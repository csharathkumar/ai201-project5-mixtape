# Mixtape — Bug Hunt Submission

## Milestone 1: Codebase Map

### Setup

Forked to `csharathkumar/ai201-project5-mixtape`, cloned locally, working branch `bugfix/mixtape` created off `main`. `app.py`, `models.py`, `seed_data.py`, all of `routes/`, `services/`, and `tests/` compile cleanly (`python -m py_compile`). App confirmed running locally via `FLASK_APP=app:create_app flask run`, responding at `http://127.0.0.1:5000`. The five open issues and their affected files are listed in `README.md`; the full issue reports (reproduction steps, expected vs. actual) are below and confirm the hypotheses formed from reading the code.

### Main files

`app.py` is the Flask application factory. It builds the app, wires up `SQLALCHEMY_DATABASE_URI` (defaulting to a local `mixtape.db` SQLite file), initializes the shared `db` object, registers four blueprints (`songs`, `playlists`, `users`, `feed`), and calls `db.create_all()` inside an app context. There's no business logic here — it's purely wiring.

`models.py` defines six SQLAlchemy models plus three association tables. `User` holds streak state directly (`listening_streak`, `last_listened_at`) rather than deriving it — so streak logic is a mutation, not a query. `Song` carries `shared_by`/`shared_at`, tying every song to the friend who shared it (this is what notification logic keys off of). `ListeningEvent` is an append-only log of plays, one row per listen. `Rating` has a unique constraint per `(user_id, song_id)`, so rating is upsert-style, not append-only. `Playlist` uses `playlist_entries` as its join table, which — unlike `friendships` and `song_tags` — carries extra columns: `position` (explicit ordering, not insertion order), `added_by`, and `added_at`. `Notification` is a flat table with a `notification_type` string and a pre-rendered `body`; there's no templating layer, each service call constructs the human-readable string inline at creation time.

`routes/` is a thin layer over four blueprints (`songs.py`, `playlists.py`, `users.py`, `feed.py`). Every route follows the same shape: parse `request.args`/`request.get_json()`, call exactly one service function, catch `ValueError` and turn it into a 400/404 JSON response, otherwise return `.to_dict()` output as JSON. No route does its own DB querying or business logic.

`services/` is where everything actually happens, split by domain: `streak_service.py` (streak increment/reset), `feed_service.py` (friends-listening-now + activity feed), `search_service.py` (song search by title/artist), `notification_service.py` (creating and reading notifications, plus `rate_song`/`add_to_playlist` which double as the "trigger" points for notifications), `playlist_service.py` (playlist CRUD-lite and ordered song retrieval).

`seed_data.py` wipes and rebuilds the DB with 5 friended users, 25 songs (deliberately split into 0-tag / 1-tag / 3+-tag groups — the comments in the file flag that the 3+-tag group is what exposes the search duplicate bug), 3 playlists of 5-10 songs each, and a mix of recent (~10-25 min old) and older (2-58 hours old) listening events to exercise the "listening now" recency filter.

`tests/` covers three of the five services (streaks, search, playlists) with fixtures that isolate an in-memory SQLite DB per test. Notably, several test docstrings/comments already name the expected bug behavior directly — e.g. `test_search_no_duplicates_multi_tag_song` says "Should be 1, bug causes it to be 3," and `test_playlist_returns_all_songs` says "Bug causes this to return 4." These read like they were written test-first against the intended fix, which makes them useful oracles once I start fixing rather than just describing symptoms.

### Data flow — user rates a song

`POST /songs/<song_id>/rate` in `routes/songs.py` pulls `user_id` and `score` from the JSON body, validates presence, and calls `notification_service.rate_song(user_id, song_id, int(score))`. That function (despite living in `notification_service.py`, not a rating-specific module) validates the score range, loads the `Song` and `User`, checks for an existing `Rating` row for that `(user_id, song_id)` pair, and either updates the existing row's score or inserts a new one — then commits and returns the `Rating`. The route serializes it back as `rating.to_dict()` with a 201.

The notable thing: `rate_song` never calls `create_notification`. Compare this to `add_to_playlist` in the same file, which — after appending the song to the playlist — explicitly checks `if song.shared_by != added_by_user_id` and creates a `song_added_to_playlist` notification for the sharer. `rate_song` has no equivalent block. This lines up exactly with issue #4 ("notified when added to playlist but not when rated") — the notification-on-rating code path simply doesn't exist yet, it's not a matter of it firing incorrectly.

### Data flow — user views a playlist's songs

`GET /playlists/<id>/songs` → `routes/playlists.py:get_songs` → `playlist_service.get_playlist_songs(playlist_id)`. That function loads the `Playlist` (404s via `ValueError` if missing), then joins `Song` to `playlist_entries` filtered by `playlist_id`, ordered ascending by `position`. The last line is `return [song.to_dict() for song in songs[:-1]]` — it drops the final element of the already-correctly-ordered list. This is issue #5 ("the last song in a playlist never shows up") and it's a one-line slicing bug independent of the query itself, which is otherwise correct.

### Patterns noticed

Routes never touch the database directly except `routes/users.py:get_user`, which calls `db.session.get(User, user_id)` inline instead of delegating to a service — the one exception to the "routes only call services" rule.

Every service function that mutates state re-validates its foreign keys by loading the referenced rows (`db.session.get(...)` then `raise ValueError` if `None`) before doing anything else, and every route converts that `ValueError` into an HTTP error response. This is a consistent, deliberate error-handling contract across the whole app, not something applied ad hoc per route.

Cross-cutting side effects — like notifications — are triggered from inside the service that owns the primary action (`add_to_playlist`, `rate_song`) rather than from a separate observer/event layer. This means whether a given user action notifies anyone at all depends entirely on whether that specific service function remembered to call `create_notification`. There's no central registry of "which actions notify" — bugs of the "some actions notify, some silently don't" shape (issue #4) are a direct consequence of this pattern, since each function is a separate hand-written call site rather than a table-driven dispatch.

Several `services/*.py` docstrings describe the *intended* behavior precisely (e.g. streak_service's docstring spells out the exact day-boundary rules; feed_service's module docstring says `get_friends_listening_now` should be "filtered by recency"), and the actual bugs are narrow deviations from those stated rules rather than wholesale misunderstandings — e.g. `update_listening_streak`'s `elif days_since_last == 1 and today.weekday() != 6:` has an extra, undocumented Sunday special-case that isn't mentioned in the docstring's "streak rules" and isn't matched by the corresponding logic anywhere else, which is consistent with issue #1.

### Issue #3 — NOT reproducible with current dependencies (swapped out)

How I tried to reproduce it: `curl "http://127.0.0.1:5000/songs/search?q=Anthem"` against "Crown Heights Anthem" (a seeded song with 3 tags — `rap`, `hip-hop`, `boom bap`). The bug is still latent in the code (the query has no explicit `.distinct()` and relies entirely on this ORM behavior to mask it), but it isn't observable as written against `requirements.txt`'s pinned `sqlalchemy>=2.0.0`. Per the milestone's guidance to swap to a different issue when one won't reproduce, moved to Issue #1.

## Milestone 3: Root Cause Analysis and Fixes

### Issue #1 — My listening streak keeps resetting

**How I reproduced it:** Called `update_listening_streak` directly with controlled UTC datetimes rather than going through the live server, since `record_listening_event` always stamps events with `datetime.now()` and I can't make "now" land on a real Sunday on demand. Simulated a Saturday listen (`2024-06-15`) followed by a Sunday listen (`2024-06-16`) — two genuinely consecutive calendar days. Confirmed via `pytest tests/test_streaks.py -v`: `test_streak_increments_on_sunday` failed with `assert 1 == 2` before the fix — the streak reset to 1 instead of incrementing to 2.

**How I found the root cause:** Started at `models.py` to see that streak state (`listening_streak`, `last_listened_at`) is stored directly on `User`, not derived — so the bug had to be in whatever mutates those fields. Traced `POST /songs/<id>/listen` in `routes/songs.py` → `streak_service.record_listening_event` → `update_listening_streak`. Read the function's docstring first ("Streak rules: ... If the user listened yesterday: streak increments by 1."), then read the actual implementation line by line. The `if/elif/else` on `days_since_last` matched the docstring except for one clause: `elif days_since_last == 1 and today.weekday() != 6:`. That `and today.weekday() != 6` isn't mentioned anywhere in the docstring's stated rules, isn't referenced by any other function, and `weekday() == 6` is exactly Sunday in Python's convention — the same day kenji's report named twice. That was the moment I was confident: a documented rule with an extra, undocumented exception that happens to match the reported day exactly.

**The root cause:** `update_listening_streak`'s increment branch requires both `days_since_last == 1` *and* `today.weekday() != 6`. On a day-to-day basis this second condition is almost always true and the bug hides — but whenever "today" (the day of the current listen) is a Sunday, the condition is `False`, so control falls through to the `else` branch and the streak resets to 1 instead of incrementing, even though exactly one day passed since the last listen (the correct condition for incrementing, per the function's own docstring). It's a boundary condition tied to the wrong variable, essentially: the code special-cased a day of the week that the stated business rule never mentioned.

**My fix and side-effect check:** Removed the `and today.weekday() != 6` clause, leaving `elif days_since_last == 1:` as the sole condition for incrementing — this is the smallest change that removes the erroneous exception without touching the same-day (`days_since_last == 0`) or skipped-day (`else`) branches at all. Verified with `pytest tests/ -v`: all 13 tests pass, including all 5 in `test_streaks.py` (the other 4 streak tests — new user, consecutive day, same-day no-op, skipped-day reset — were passing before and still pass, confirming the fix didn't regress the other boundaries). Also manually reasoned through the adjacent boundary (Saturday → Sunday → Monday, i.e., checking the fix doesn't accidentally treat Monday specially either) — the new condition is day-of-week-agnostic entirely, so there's no equivalent hidden case on the other side.

### Issue #4 — I got notified when a friend added my song to a playlist but not when they rated it

**How I reproduced it:** Used real seeded IDs (queried directly from `instance/mixtape.db`) — "Midnight Drive," shared by nova, rated by darius (a different user). Checked nova's notifications (`GET /users/<nova_id>/notifications`) before and after `POST /songs/<song_id>/rate`. Before the fix: baseline showed 1 notification (a `song_added_to_playlist` from seed data); after a successful `201` rating response, the count was still 1 — no new notification, matching aaliya's report exactly (rating saves fine, but nothing shows up in notifications, no delay).

**How I found the root cause:** Traced `POST /songs/<id>/rate` in `routes/songs.py` to `notification_service.rate_song` — notable immediately that this function lives in `notification_service.py` despite being a rating function, which is a hint that it's supposed to handle notifications too. Read `rate_song` top to bottom: validates score, loads `Song`/`User`, upserts the `Rating` row, commits, returns. No call to `create_notification` anywhere. To confirm this was really the gap and not, say, a filtering bug in `get_notifications`, I compared `rate_song` side-by-side with `add_to_playlist` in the same file — the latter has an explicit block after its own commit: `if song.shared_by != added_by_user_id: create_notification(...)`. `rate_song` has no equivalent block at all. That direct structural comparison (identical surrounding pattern — validate, mutate, commit — except one has the notify step and one doesn't) was what confirmed this was a missing step, not a broken one.

**The root cause:** `rate_song` never calls `create_notification`. The notification side-effect for playlist adds is hand-written directly inside `add_to_playlist`, and no equivalent code was ever written inside `rate_song` — there's no shared dispatch mechanism connecting "user action" to "notify the sharer," so each action's notification behavior is only as complete as whoever wrote that specific function remembered to make it. This function's author simply didn't add the notify step.

**My fix and side-effect check:** Added a block after the rating commit, structurally identical to `add_to_playlist`'s: `if song.shared_by != user_id: create_notification(user_id=song.shared_by, notification_type="song_rated", body=f"{rater.username} rated your song '{song.title}' {score} stars.")`. This only fires when the rater isn't the song's own sharer (self-ratings don't self-notify, matching the same self-check `add_to_playlist` already does). Verified live: rated "Midnight Drive" as darius, nova's notification count went from 1 to 2, with the new entry reading `"darius rated your song 'Midnight Drive' 3 stars."` — correct type (`song_rated`) and body. Checked for regressions: `get_notifications` and `mark_as_read` don't filter by `notification_type`, so the new type flows through existing retrieval code with no changes needed there. Also checked that re-rating a song (the `existing` branch of `rate_song`) still notifies — this mirrors `add_to_playlist`'s own existing behavior of notifying unconditionally on every call rather than only on first-time adds, so the fix is consistent with the codebase's current (if debatable) convention rather than introducing a new one.

### Issue #5 — The last song in a playlist never shows up

**How I reproduced it:** Looked up playlist "Late Night Vibes" directly in `instance/mixtape.db` — 7 rows in `playlist_entries` for that playlist ID. Called `GET /playlists/<id>/songs` and got back `{"count": 6, ...}` — one fewer than the DB actually has, with the missing song always being the one with the highest `position`. This matches darius's report precisely (playlist "says" 7, shows 6, and the missing song is always the most recently added one).

**How I found the root cause:** Followed `GET /playlists/<id>/songs` → `routes/playlists.py:get_songs` → `playlist_service.get_playlist_songs`. Read the query first: joins `Song` to `playlist_entries` filtered by `playlist_id`, ordered ascending by `position` — correct, and matches the docstring ("Songs are returned in the order they were added"). The very next and final line is `return [song.to_dict() for song in songs[:-1]]`. The query itself builds the right list; the only thing touching it afterward is that slice. Cross-referenced with `tests/test_playlists.py::test_playlist_returns_all_songs`, whose inline comment already says "Bug causes this to return 4" for a 5-song playlist — an off-by-one that only makes sense if something drops exactly one element after an otherwise-correct fetch, which is exactly what `songs[:-1]` does.

**The root cause:** `get_playlist_songs` unconditionally slices off the last element of the already correctly-ordered song list (`songs[:-1]`) before returning it. Since the query orders by `position` ascending, the last element is always the song with the highest position — i.e., the most recently added one. The function's own docstring even states "This function returns all songs in the playlist," directly contradicted by the slice on the return line.

**My fix and side-effect check:** Removed the slice, changing `songs[:-1]` to `songs` — the smallest possible change, since the query logic itself was already correct. Verified with `pytest tests/test_playlists.py -v`: all 3 tests pass, including `test_playlist_returns_all_songs` (now correctly returns 5 for a 5-song playlist) and `test_playlist_returns_songs_in_order` (confirms the fix didn't disturb ordering — still `["Track 1", ..., "Track 5"]`). Verified live against real seed data too: "Late Night Vibes" went from `count: 6` to `count: 7`, with "Free Throws" (previously the hidden song) now present. Checked the boundary on the other side — `test_empty_playlist_returns_empty_list` still passes, confirming the fix doesn't break the zero-songs case (`[][: -1]` and `[]` were already equivalent, so this was never at risk, but worth confirming explicitly since Issue #5 is a boundary-condition bug).
